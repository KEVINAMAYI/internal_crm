## Product summary

An internal, merchant-centric CRM for a payments processor, used by Sales, Support, and Ops. Single
view per merchant: profile, contacts, read-only transaction history, support tickets,
activity/notes, and tasks.

**Stack (planned):** Supabase (Postgres + Auth + Row-Level Security + auto-generated PostgREST/
Realtime APIs) on the backend; React (Vite + TypeScript) + `@tanstack/react-query` +
`react-router-dom` + shadcn/ui on the frontend. No custom backend server — the SPA talks directly
to Supabase; authorization is enforced entirely at the database layer via RLS, not in application
code.

## Core architecture (from TECHNICAL_IMPLEMENTATION.md)

- **Entities:** `profiles` (app users, mirrors `auth.users`), `merchants`, `contacts`,
  `transactions` (read-only to the app), `support_tickets`, `activities` (notes/calls/timeline,
  optionally linked to a ticket), `tasks`. Everything hangs off `merchants` — see §2.3 for the ER
  summary.
- **Roles:** `sales`, `support`, `ops`, `admin`, stored on `profiles.role`. A custom access-token
  hook (`custom_access_token_hook`, §3.2) injects the role into the JWT (`app_metadata.role`) at
  token issue so RLS policies can read it without a per-query `profiles` lookup
  (`auth.role_name()` helper).
- **Authorization is DB-side only.** Every table has RLS enabled; policies (§3.4) are the real
  permission boundary. Frontend role checks (`RequireRole`, disabled buttons) are UX convenience —
  never the enforcement mechanism. Read the role/table permission matrix in §3.1 before adding any
  write path.
- **Transactions are strictly read-only to all app roles**, including admin. The only writer is a
  `service_role` ingestion path (Edge Function or batch job, §4.5) that bypasses RLS entirely —
  never add insert/update/delete UI or policies for `transactions`.
- **No custom REST layer.** PostgREST auto-generates the API from the schema; the frontend uses the
  typed `@supabase/supabase-js` query builder directly (`src/api/*.ts` per entity, per the planned
  structure in §5.1), with types generated via `supabase gen types typescript`. Nested reads use
  PostgREST embedded resources (e.g. `select('*, contacts(*)')`) instead of separate round trips.
- **Heavy aggregation goes through `security definer` SQL functions** called via `supabase.rpc()`
  (e.g. `merchant_summary` for 30-day volume/txn count/open tickets, §4.3) rather than being
  computed client-side.
- **Realtime** subscriptions are scoped per merchant (`merchant:${id}` channel) for `activities`,
  `support_tickets`, and `tasks`, invalidating react-query cache keys on change — multiple agents
  may be viewing the same merchant concurrently.

## UI architecture (from docs/ui_ux_plan.md)

- Merchant-centric master-detail: a persistent left sidebar (module nav: Merchants, Tickets, Tasks,
  Admin) plus, within Merchants, a list/detail split view. Merchant Detail uses a tab strip
  (Activity, Contacts, Tickets, Transactions, Tasks) rather than separate routes, deep-linked via
  `/merchants/:id?tab=...` so header context (status, KPIs) persists across tabs.
  Also `/merchants/:id?tab=tickets&ticket=<id>` for an expanded ticket row.
- Global cross-entity search is a topbar ⌘K command palette (merchants/tickets/tasks), implemented
  as a lightweight PostgREST query, not a separate search index.
  There is also a global Tickets queue (cross-merchant triage view) and a standalone Tasks home
  ("My Tasks" / "Assigned by Me" / "Team" / "Unlinked") for tasks not tied to a merchant.
- Permission gating rule of thumb (see full matrix in `docs/ui_ux_plan.md` §5): **hide** controls
  that are role-impossible by design (e.g. Support never sees "New Merchant"; nobody ever sees any
  transaction write control); **disable + tooltip** controls that are data-ownership-dependent
  (e.g. Sales can edit their own merchants but not others'). Every mutation still goes through the
  normal Supabase call and must handle RLS rejection with a toast — never assume a UI-permitted
  action will succeed.
- Inline `Select` + optimistic update for single-field, low-risk edits (ticket status/priority/
  assignee, task status); `Dialog`/`Sheet` forms for multi-field creates/edits; an inline composer
  (not a modal) for logging activity notes, since it's the highest-frequency action.
